# План доработки: авторизация для tdtpserve

Статус: **реализовано** (`auth.go`, `ratelimit.go`, `auth_test.go`,
`auth_hardening_test.go`; конфиг в `config.go`, маршруты в `server.go`).
Использование — в README.md, раздел "Авторизация". Ниже — исходный план и
обоснование решений, актуальны как есть.

## Добавлено после первой версии

Первая версия оставляла три дыры — не ошибки в логике, а незакрытые края.
Все три закрыты:

1. **Рост `TokenStore` не был ограничен.** Протухшая запись удалялась только
   при повторной валидации того же токена, то есть никогда, если клиент за
   ним не возвращался. `/api/login` неаутентифицирован, так что выдачу можно
   было крутить в цикле. Теперь: уборка протухших при выдаче (там же, где
   карта единственно и растёт — отдельная горутина-уборщик не нужна) и
   потолок `maxLiveTokens = 10000`, сверх которого логин отказывает.
   Отказавший логин повторяют; сервер, убитый OOM, уносит все сессии.
2. **Не было предела на попытки входа.** Каждый вызов `/api/login` стоит
   ~60 мс CPU на bcrypt — цена намеренная, но она же делает неаутентифицированный
   маршрут усилителем DoS. Теперь 10 попыток в минуту на адрес
   (`ratelimit.go`), проверка стоит **до** bcrypt, иначе она не ограничивала
   бы то, ради чего написана.
3. **Тело запроса не было ограничено.** `http.MaxBytesReader` на 4 КБ:
   учётные данные — две короткие строки.

Заодно появился `POST /api/logout` (за `requireAuth`, отзыв только своего
токена): без него токен, попавший не туда, оставался годным до конца TTL, и
единственным средством был рестарт сервера.

Что осознанно осталось незакрытым — в README.md, раздел «Чего здесь нет»
(TLS, `X-Forwarded-For`, потеря токенов при рестарте, отсутствие ролей).

## Зачем

`/api/*` уже спроектирован так, чтобы позже можно было навесить контроль доступа
отдельно от HTML-страниц (`api.go`, `lookup.go` — отдельный префикс специально
для этого). До появления авторизации разделение контуров (например, кадровый
и финансовый) обеспечивается только тем, что это разные процессы на разных
портах — см. README.md. Это разделяет *данные*, но не ограничивает *кто* может
подключиться к порту — этим занимается firewall/bind-адрес, вне кода tdtpserve.

## Схема: логин по паролю → токен с ограниченным временем жизни

```
POST /api/login {"username": "...", "password": "..."}
  → bcrypt.CompareHashAndPassword(hash, password)
  → если ок: crypto/rand → 32 случайных байта → токен
  → сохранить в памяти: map[token]{username, expiresAt: now+ttl} под sync.RWMutex
  → ответ: {"token": "...", "expires_at": "..."}

Каждый следующий запрос к /api/* (кроме /api/login):
  Authorization: Bearer <token>
  → найти в мапе → проверить expiresAt > now → иначе 401
```

## Ключевые решения и почему

**Пароль → bcrypt, не SHA-256.** `cmd/orchestrator/auth.go` уже хеширует свои
API-токены через SHA-256 — это нормально для *токена* (уже высокоэнтропийная
случайная строка). Пароль — человеческий, угадываемый, поэтому нужен
намеренно медленный, соленый хеш (bcrypt/argon2), иначе SHA-256
брутфорсится на GPU за приемлемое время. `golang.org/x/crypto/bcrypt` уже
доступен как непрямая зависимость (`go.mod`, v0.53.0) — новый пакет не нужен,
только явный import.

**Непрозрачный токен (map в памяти), не JWT.** Осознанный выбор для
одного процесса/внутреннего инструмента: без новой зависимости, мгновенный
revoke (удалить из мапы), допустимая потеря токенов при рестарте (перелогин —
дешёвая операция). JWT дал бы самоверификацию без состояния, но сложнее
ранний revoke и добавляет библиотеку — не оправдано здесь.

**Область действия — весь `/api/*`, кроме `/api/login`.** HTML (`/`, `/data/`)
— отдельное решение по месту: оставить открытым для удобства во внутренней
сети или защитить так же, в зависимости от того, насколько публично стоит
конкретное развёртывание.

## Конфиг (черновой)

```yaml
auth:
  enabled: true
  token_ttl: 30m
  users:
    - username: hr_app
      password_hash: "$2a$10$..."   # сгенерирован офлайн, никогда не plaintext в yaml
```

Хеш пароля генерируется отдельной командой/режимом (например
`tdtpserve --hash-password <pw>`), чтобы plaintext пароль никогда не
записывался в конфиг вручную.

## Черновой план реализации

1. `AuthConfig`/`UserConfig` в `config.go` + валидация (`enabled`, `token_ttl`,
   непустой `users`, у каждого — `username`+`password_hash`).
2. `auth.go` (новый файл): `TokenStore` (`map[string]tokenInfo` +
   `sync.RWMutex`), `Issue(username) (token string, expiresAt time.Time)`,
   `Validate(token) (username string, ok bool)` — сразу отбрасывает
   просроченные записи при проверке (лениво, без отдельной горутины-уборщика
   на первую версию).
3. `handleAPILogin` (`POST /api/login`) — сверяет пароль через bcrypt,
   вызывает `TokenStore.Issue`, отвечает `{token, expires_at}`. Неверный
   логин/пароль → `401` (без уточнения, что именно неверно — не давать
   подсказок для перебора).
4. Middleware-обёртка над существующими `/api/*` хендлерами (кроме
   `/api/login`) — читает `Authorization: Bearer <token>`, зовёт
   `TokenStore.Validate`, `401` при отсутствии/невалидности/просрочке.
5. `cfg.Auth.Enabled == false` (или секция отсутствует) — полностью
   пропускает мидлварь, поведение как сегодня (обратная совместимость по
   умолчанию).
6. Тесты: успешный логин → валидный токен → доступ; неверный
   пароль → 401 на логине; просроченный токен → 401 на запросе; запрос без
   заголовка → 401; `auth.enabled: false` → доступ без токена (регресс на
   сегодняшнее поведение).
7. README.md: раздел "Авторизация" рядом с существующими "JSON API" и
   "Lookups".

## Не входит в эту итерацию (сознательно)

- Refresh-токены — для внутреннего инструмента перелогин по истечении TTL
  проще и достаточно.
- Ролевой доступ (admin/consumer, как в orchestrator) — можно добавить позже
  тем же принципом (`role` в `UserConfig`), не блокирует первую версию.
- Хранение пользователей в БД вместо YAML — YAML достаточен, пока список
  пользователей небольшой и меняется редко (перезапуск сервера для
  добавления пользователя — приемлемо для внутреннего инструмента).
